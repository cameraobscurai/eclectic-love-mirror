# Ceilings audit — 2026-08-12

Three independent read-only audits: XLSX round-trip feasibility, structural ceilings,
owner self-serve gaps. Findings below are verified against code, not memory.

---

## 1. The Squarespace-style XLSX loop — yes, buildable

`xlsx` (SheetJS 0.18.5) is already in `package.json`. Pure JS, Worker-safe.
The blocker is not the library; it's that every spreadsheet path today is a CLI
script (`scripts/import.mjs`, `scripts/apply-taxonomy.mjs`) that needs a laptop.

Shape:

```text
/admin/inventory
  ├─ Download workbook  → exportInventoryXlsx()        (whitelisted columns only)
  ├─ Upload edited file → stageInventoryUpload()        (parse, join on id, diff)
  ├─ Review diff        → red/green table, per-row opt-out
  └─ Apply              → applyInventoryBatch()         (one audit row per change)
```

Round-trippable: `title`, `description`, `quantity`, `quantity_label`,
`dimensions_raw`, `price`, `status`, `public_ready`.

NEVER round-trippable (R6 boundary, enforced at diff time, not just import time):
`id`, `rms_id`, `slug`, `images`, `collection_slug`, `category_slug`,
`taxonomy_review`. Taxonomy stays in the Studio where the pair is validated.

Five ways this goes wrong, all avoidable:

1. `xlsx.readFile()` is an `fs` call — must be `xlsx.read(buffer, {type:'array'})` in the Worker.
2. Reusing the diff logic instead of the `updateProduct` allow-list re-opens the R6 hole.
3. Zipping rows by position instead of joining on `id` — Excel sort silently mismatches every row.
4. 850 individual updates with no transaction — a mid-batch failure leaves half-applied state.
5. `admin_audit_log` writes on product edits are a DB trigger, not app code. A bulk path
   that bypasses it leaves the diff/approve trust model unaudited. Verify before building.

## 2. Structural ceilings, ranked

| #   | Ceiling                                                                                                       | Trigger                                       | Smallest fix                                             |
| --- | ------------------------------------------------------------------------------------------------------------- | --------------------------------------------- | -------------------------------------------------------- |
| 1   | `current_catalog.json` is one 1.1MB blob, fetched whole on first catalog read                                 | ~3.5MB parse at 2000 items                    | Split per collection, or query Supabase for list views   |
| 2   | Two sources of truth: overlay (live) vs baked JSON (needs a laptop + commit)                                  | Any field outside the overlay's list          | Move `bake-catalog.mjs` into a triggered server function |
| 3   | 38 scripts, most load-bearing, all developer-only, chained by "next run bake" comments                        | Every taxonomy/cover fix                      | Wrap the apply→bake chains into one idempotent job       |
| 4   | 21 `/admin` routes; `colors`, `image-health`, `render`, `image-qa` are dev instrumentation on the owner's nav | Now                                           | Move behind an Advanced section                          |
| 5   | Frame Studio falls back to the old live solver per-row, with no backfill deadline                             | 20% ungraded at 2000 items = 400 broken tiles | Force-draft `cover_framed_url` for all ungraded rows     |
| 6   | `frame-engine.ts` — the keystone — has no unit test                                                           | First bulk auto-frame run                     | bbox/verifier unit tests before any batch                |
| 7   | All 7 specs are Playwright/visual. Zero coverage of bake, merge, or publish correctness                       | A bad merge nulls `images` and CI stays green | One unit test on bake output shape                       |
| 8   | CI never re-bakes or diffs the JSON against the DB                                                            | Stale commit ships wrong data, green build    | CI drift detector: re-bake, fail if tree is dirty        |

Ceilings 1, 2, and 3 are the same disease: **the pipeline's last mile runs on a
developer's laptop.** Fixing #2 removes most of #3 and de-risks #8.

## 3. What still needs an engineer

Blocking, hardest first:

1. **Bulk edit** — no multi-select in `/admin/products`. 50 items = 50 drawers.
2. **Export a list** — no CSV/XLSX button anywhere. Vendor or insurance list = a DB query.
3. **Undo a deletion** — product delete is permanent. Inquiries already have
   `restoreInquiries`; products have nothing. Only a DB backup recovers it.
4. **Fix a broken photo** — `/admin/image-health` reports failures, it doesn't fix them.
5. **Color QA, AI render pipeline** — cost-bearing dev tools on her nav.

Traps worth naming:

- Search hint advertises "RMS id, slug".
- `/admin/photos` UI text literally says "no bake needed".
- "Save & mark ready" and the global Publish button are separate — new products can
  sit saved-but-invisible.
- `PublishBar` surfaces the raw JS error string in an ALL CAPS toast.
- Two different UIs edit taxonomy (`/admin/products` drawer and `/admin/taxonomy`).
- Half the call sites use `runAdminMutation` plain-English errors, half throw raw
  `Error.message` into the UI.

---

## Recommended order

1. **Product trash + restore, and the XLSX export half of the loop.** Small, reversible,
   and export alone answers most of what she means by "manage a spreadsheet".
2. **XLSX upload → diff → approve.** The other half. Confirm the audit-log trigger first.
3. **Bake as a server function.** Removes the laptop from the last mile — ceilings 2, 3, 8.
4. **Hide dev tools from her nav; unify error copy.** One afternoon, large perceived gain.
5. **Frame engine tests + ungraded backfill deadline.** Before any bulk auto-frame.
